# 实施计划: GitHub 发布整理与配置外显化

## 实现方向

这轮变更分成两层：先收敛运行模型与验证码实现，再做公开仓库整理。整体方向分成五部分：

1. 巡检调度外显化：把“每天 8:00 到 18:00 每小时检查一次，有新候选就自动报名”做成明确的运行模式，并优先通过配置文件表达，而不是依赖用户自己推导 `pollIntervalMs` 和 `maxCycles`。
2. 验证码实现收敛：彻底移除 `tesseract.js` 路径，统一改成通过 Python `ddddocr` 脚本完成验证码识别，并保留最多 5 次重试限制。
3. 仓库发布整理：清理不应保留的文件，补齐 `.gitignore` 和公开仓库应有的模板文件。
4. 使用说明外显化：用 README 把安装、配置、运行、校园网内外两种登录路径、验证码、邮箱验证以及后台运行方式写清楚。
5. 时间段配置模型升级：把当前巡检时间和筛选时间都收敛为“每天可配置多个不连续时间段”的数组结构，使个人偏好保留在配置文件中，而公开仓库只保留模板与说明。`.env` 继续只保留账号密码等敏感信息。

实现上优先保持现有登录与报名主工作流稳定，不重写业务链路，而是在配置层和工作流调度层增加更明确的公开接口。配置模型上采用“双层配置”：`.env` 负责敏感信息，配置文件负责可公开的运行参数与筛选规则。

## 执行顺序

1. 先收敛配置文件结构，明确 `.env` 只放敏感信息，公开配置全部进入 JSON 配置文件。
2. 把巡检模式和筛选模式都改成数组时间段模型，支持同一天多个不连续区间。
3. 删除 `tesseract.js` 路径与相关配置字段，统一改成 `ddddocr` 执行链路。
4. 盘点当前仓库结构，确定哪些文件应删除、哪些应忽略、哪些应重建。
5. 整理 `.gitignore`，同时恢复新的 `.env.example` 与配置文件模板。
6. 为 `macOS/Linux` 与 `Windows` 封装统一运行脚本，并让 README 以脚本为主要执行入口。
7. 调整 README，面向公开用户完整说明配置项、运行方式、后台运行方式和校园网内外两种使用场景。
8. 做基础验证，确认代码、测试和文档中的命令都与当前仓库结构一致。
9. 更新结果文档和稳定事实文档，记录新的公开发布约束与配置方式。

## 依赖与输入

1. 当前已有的 Node.js、Playwright、TypeScript 自动化代码。
2. 当前已经验证过的真实登录行为，包括校园网外可能出现验证码和新设备邮箱验证。
3. 当前硬编码的时间筛选规则实现，作为新配置模型的业务基线。
4. 用户新增的运行要求：在每天 8:00 到 18:00 之间，每小时自动检查一次讲座信息。
5. 用户新增的配置建议：配置模型优先使用配置文件，而不是命令行参数。

## 关键风险

1. 巡检调度和筛选规则同时切换到数组时间段模型时，容易在默认值兼容和文档表达之间出现不一致，因此需要先统一结构再更新 README。
2. 删除 `tesseract.js` 后，验证码成功率将完全取决于本地 `ddddocr` 环境，因此必须把 Python 依赖与脚本入口说清楚。
3. 仓库清理时如果误删运行所需脚本或模板，可能导致 README 和真实代码不一致。
4. 如果配置文件与 `.env` 的边界没有划清，最终 README 会同时存在两套互相冲突的配置方法。
5. README 如果没有把“验证码出现时需要 `headful`”“邮箱验证需要人工完成”以及“后台运行时如何观察失败日志”写清楚，公开用户仍然会误用。
6. `.gitignore` 只能屏蔽未跟踪文件；对已经跟踪过的历史文件，需要通过本轮仓库整理明确地删除或替换。

## 验证方案

1. 对配置层、调度层与验证码层执行 `npm run typecheck` 和 `npm test`，确认新的配置文件模型、巡检模式、筛选配置接口和 `ddddocr` 配置接口没有破坏现有逻辑。
2. 人工检查 `.env.example`、配置文件模板与 README 中的变量说明是否一致。
3. 人工检查 README 中的命令是否与 `package.json` 脚本一致。
4. 人工检查 README 中的脚本入口与后台运行方法是否覆盖至少 macOS / Linux 与 Windows。
5. 人工检查筛选条件与巡检时间段配置说明是否能覆盖“单日多个不连续时间段”的场景。
6. 人工检查 `.gitignore` 是否覆盖 `.env`、配置文件本地实例、本地缓存、日志、Playwright 产物、虚拟环境和本地实验文件。

## 面向用户的任务拆分

1. 用配置文件定义一个每天 8:00 到 18:00 每小时巡检并自动报名的公开运行模式，并允许多个时间段。
2. 清理验证码实现，统一切到 `ddddocr`。
3. 清理仓库结构并补齐对外发布所需的忽略规则、`.env.example` 和配置文件模板。
4. 完成 README，写清楚配置项、校园网内外的运行方式、后台运行方式、验证码/邮箱验证处理方式以及两层配置步骤。
5. 将时间筛选规则改造成个人配置文件，而不是源码常量或长命令行参数。
6. 提供跨平台运行脚本并回归验证，记录新的公开发布事实。

## 当前结论

当前范围、执行顺序和风险都已足够明确，可以继续执行。后续实现应先统一配置模型和 `ddddocr` 验证码链路，再完成数组化时间段、脚本封装与 README 收尾，因为公开文档必须以最终接口为准。
