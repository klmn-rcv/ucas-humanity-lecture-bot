# 实施计划: SEP 验证码现场验证

## 实现方向

本轮不以新增功能为主，而是以“真实验证码场景下的闭环验证和必要修正”为主。核心策略是继续使用现有 `Playwright + tesseract.js` 登录链路，在用户切换网络环境并触发验证码后，先用 `--headful --dry-run` 做可观察验证，再根据真实页面反馈决定是否需要修正验证码选择器、OCR 归一化或重试逻辑。

整体工作分为四层：

1. 现场触发层：由用户切换网络环境，让 SEP 登录页真实出现验证码。
2. 登录验证层：运行当前自动化，观察验证码检测、截图、识别、回填、提交和重试行为。
3. 最小修正层：如果现场出现选择器失配、图片抓取失败、OCR 输出异常或刷新逻辑无效，则对 `src/captcha.ts` / `src/login.ts` 做最小必要修改。
4. 回归确认层：在验证码链路修正后，重新执行一次登录和一次 `dry-run`，确认不会破坏已验证过的讲座页访问能力。

## 执行顺序

1. 先在当前代码基线上检查验证码相关实现与日志点，明确本轮重点观察项。
2. 等待用户切换网络环境后，使用真实 `.env` 和 `--headful --dry-run` 运行登录流程，确认验证码是否出现。
3. 如果验证码出现，记录验证码控件、刷新行为、OCR 原始文本、归一化结果和登录结果。
4. 如果验证码识别失败，区分是 OCR 失败、选择器错误、验证码刷新失败，还是登录页还有额外校验。
5. 针对真实问题做最小修正，并优先补上自动化测试或最小回归测试。
6. 修正后重新做一次真实验证码登录验证，再执行一次讲座页 `dry-run`，确认主流程未回归。
7. 更新结果文档和稳定事实文档，记录真实验证码样式、已验证行为和剩余风险。

## 依赖与输入

1. 用户提供的真实 UCAS 账号密码，已通过本地 `.env` 管理。
2. 用户切换后的网络环境，能让 SEP 登录页真实出现验证码。
3. 本地可运行的 Playwright 浏览器与 `tesseract.js` 依赖。
4. 允许以 `--headful` 方式运行，以便在现场验证中观察真实验证码与错误反馈。

## 关键风险

1. 用户切换网络环境后，验证码仍不一定稳定出现，因此第一轮执行可能只能确认“当前条件下仍未触发验证码”。
2. 真实验证码字符集、长度、干扰线或大小写规则可能与当前 OCR 假设不一致，导致识别率偏低。
3. SEP 可能在验证码之外叠加额外校验，例如频率限制或隐藏错误提示，导致“OCR 看似成功但仍无法登录”。
4. 为了验证验证码而调整登录逻辑时，存在破坏既有无验证码登录链路的风险，因此必须做回归验证。

## 验证方案

1. 现场验证命令优先使用 `--headful --dry-run --log-level debug`，便于观察和留存登录行为。
2. 每次验证码出现时，至少记录一次 OCR 原始输出、归一化输出和页面反馈。
3. 如果发生代码修正，执行 `npm run typecheck` 与 `npm test`，再做一次真实 `dry-run` 回归。
4. 若本轮成功通过验证码登录，再继续走到讲座页，确认 `xkcts` 会话建立没有被验证码路径破坏。
5. 若本轮未能通过验证码登录，要在结果中明确写出失败落点和下一步最优调试方向。

## 面向用户的任务拆分

1. 触发真实验证码场景并观察当前登录链路。
2. 修正验证码识别或刷新问题。
3. 重新验证登录并确认讲座页访问未回归。
4. 记录真实验证码样本特征、结果和剩余风险。

## 当前结论

当前这轮变更的范围和执行路径已经明确，外部依赖只有“用户切换网络环境后真实触发验证码”。因此本次规划可以进入 `ready`，下一步直接执行 `/spec go` 即可开始现场验证。
