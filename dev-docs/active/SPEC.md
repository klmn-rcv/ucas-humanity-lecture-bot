# 变更规格: SEP 验证码现场验证

## 目标

在用户切换网络环境、使 SEP 登录页真实出现验证码的前提下，对当前项目的验证码识别链路做一次完整现场验证，确认验证码检测、截图、OCR 识别、回填、失败重试和后续登录流程是否真实可用；如果现场验证暴露出验证码选择器、识别精度或重试策略的问题，则在同一轮执行中修正它们。

## 范围

本次变更包含以下内容：

1. 使用真实 UCAS 账号，在“登录 SEP 时出现验证码”的网络环境下执行一次受控登录验证。
2. 观察并记录登录页真实出现的验证码输入框、验证码图片、刷新行为和错误提示。
3. 验证 `src/captcha.ts` 与 `src/login.ts` 中的验证码检测、截图、OCR 回填和刷新重试是否能在真实页面上工作。
4. 如果现场验证发现验证码识别链路与真实页面不匹配，则补充必要的最小代码修正。
5. 保存本轮现场验证结论，包括是否成功穿过验证码登录、失败原因、样本特征和后续风险。
6. 在不影响现有讲座抓取与报名逻辑的前提下，重新执行至少一次 `dry-run`，确认修正没有破坏原有主流程。

## 边界

本次变更不包含以下内容：

1. 不改变现有讲座筛选规则、报名规则和次数停止规则，除非验证码验证暴露出登录前置流程必须同步修正的问题。
2. 不尝试绕过学校新增的人机验证策略；只验证当前项目已实现的图形验证码识别能力。
3. 不承诺把 OCR 调整到“任何验证码图片都高成功率”，本轮目标是基于真实样本收敛到当前 SEP 页面可验证的工作状态。
4. 不引入新的云端 OCR 服务或外部打码平台；优先继续使用本地 `tesseract.js` 能力。
5. 不把账号密码、验证码截图或其他敏感信息提交进仓库。

## 验收标准

满足以下条件时，可认为本次变更完成：

1. 在真实出现验证码的 SEP 登录页上，程序能够检测到验证码输入框和验证码图片，并输出相应日志。
2. 程序能够对真实验证码图片执行 OCR，并将识别结果回填到登录表单。
3. 如果首次识别失败，程序能够按现有策略刷新验证码并执行有限次重试，而不是卡死或无限循环。
4. 至少完成一次真实登录结果验证，并明确区分以下结果之一：验证码识别成功并继续进入后续流程、验证码识别失败、页面结构与实现不匹配。
5. 如果现场发现真实页面与当前实现不匹配，本轮执行要么修复问题并重新验证，要么在结果文档中给出可复现的明确阻塞信息。
6. 完成验证码现场验证后，现有 `--dry-run` 主流程仍能正常打开讲座页，不出现回归。

## 已知前提

1. 当前实现已经包含验证码输入框检测、验证码图片截图、`tesseract.js` OCR 和验证码刷新逻辑，但之前没有采集到真实验证码样本。
2. 2026-03-17 的前一次真实登录未触发验证码，因此现阶段的验证码能力只完成了代码实现和离线逻辑验证，尚未完成现场闭环。
3. 用户计划通过切换网络环境提高 SEP 登录时触发验证码的概率，这是本轮现场验证成立的外部前提。
