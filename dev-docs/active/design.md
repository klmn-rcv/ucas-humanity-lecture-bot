# 当前实现设计

## 总体运行流

当前项目已经从“主要依赖环境变量和命令行参数的单次脚本”演进成了“双层配置驱动的自动化工具”。一次完整运行现在按以下顺序展开：

1. `src/cli.ts` 启动后，先调用 `src/config.ts` 读取两类输入：
   - `.env` 中的敏感信息，例如 UCAS 用户名和密码。
   - `ucas-bot.config.json` 中的非敏感运行参数，例如运行模式、巡检时间、验证码配置和时间筛选规则。
2. 配置解析完成后，CLI 创建结构化日志器，并把当前运行模式、配置文件路径、是否找到配置文件、状态文件路径和筛选规则数量写入启动日志。
3. `src/workflow.ts` 根据配置决定走哪条主路径：
   - `single`：执行一次完整抓取与报名流程后退出。
   - `scheduled`：在每天 8:00 到 18:00 的配置窗口内按固定间隔反复执行单轮流程；每轮之间不保持浏览器常驻，而是重新创建新的浏览器上下文，以降低长时间挂起一个会话带来的不稳定性。
4. 每一轮实际业务流程仍然是登录、建立讲座页会话、抓取列表、套用筛选规则、在需要时执行报名、更新状态文件。
5. 定时模式下，如果一轮执行失败，工作流不会直接让整个进程退出，而是记录错误日志并继续等待下一次巡检时刻。这一点是为了让后台巡检更接近“长期挂起的任务”而不是“一次失败就结束的脚本”。

整个系统现在可以理解为五层：

1. 配置层：把敏感信息和公开运行参数分开。
2. 调度层：决定是单次执行还是按时巡检。
3. 登录与会话层：保证能从 SEP 进入人文讲座站点。
4. 抓取与筛选层：把页面转换成结构化讲座数据，并根据个人配置决定哪些讲座值得处理。
5. 报名与状态层：执行报名、识别终态、把结果写回本地状态文件。

## 配置模型

### `.env` 与配置文件的职责划分

新的配置模型明确区分了两类配置来源：

1. `.env`
   - 只负责账号密码这类敏感信息。
   - 当前至少包含 `UCAS_USERNAME` 和 `UCAS_PASSWORD`。
   - 可以额外用 `UCAS_CONFIG_PATH` 指向一个自定义的公开配置文件路径。
2. `ucas-bot.config.json`
   - 负责非敏感配置。
   - 包括日志级别、运行模式、是否 `headless`、是否 `dryRun`、状态文件路径、验证码参数、讲座站点地址和时间筛选规则。

这样做的意义有两个：

1. 公开仓库可以安全地保留 `ucas-bot.config.example.json` 作为模板，而不需要把个人偏好硬编码在源码里。
2. 用户平时调整巡检时间、开关后台模式或修改筛选条件时，不再需要改命令或改源码，只改一个公开配置文件即可。

### `src/config.ts`

这个模块现在承担三件事：

1. 用 `dotenv` 读取敏感环境变量。
2. 读取并解析 JSON 配置文件。
3. 用 `zod` 对配置做结构校验，再把它们归一化成内部统一的 `AppConfig`。

解析后的内部配置已经不再保留“原样的外部文件结构”，而是被收敛成程序真正需要的字段，例如：

1. `runMode`
2. `schedule`
3. `timeWindows`
4. `captcha`
5. `configPath` 与 `configFileExists`

命令行参数仍然存在，但作用已经明显收缩。现在它们主要用于临时覆盖，例如：

1. `--config`
2. `--dry-run`
3. `--no-dry-run`
4. `--headful`
5. `--log-level`

这说明命令行已经从“主要配置入口”降级成“临时调试覆盖入口”。

## 调度层

### `src/schedule.ts`

这个模块是本轮新增的调度辅助层，专门处理“白天按小时巡检”需要的时间计算。

它当前提供两个稳定能力：

1. 判断当前时间是否落在巡检窗口内。
2. 给定当前时间，计算下一次应该执行巡检的时刻。

目前默认窗口是：

1. 开始小时 `8`
2. 结束小时 `18`
3. 间隔 `60` 分钟

工作流不会自己猜测“下次大概什么时候跑”，而是把这个计算明确外包给调度辅助模块，从而避免把时间槽逻辑散落在主流程里。

### `src/workflow.ts`

这个模块现在分成两层：

1. `runAutomation`
   - 作为总入口，根据 `runMode` 选择单次模式或定时模式。
   - 定时模式下负责计算等待时长、睡眠到下一次巡检时间、记录调度日志。
2. 单轮执行函数
   - 每次创建新的浏览器与上下文。
   - 执行一次完整的登录、抓取、筛选、报名和状态持久化。
   - 返回本轮摘要，供日志与上层调度使用。

这轮最重要的结构变化是：原来的“一个浏览器里循环 `maxCycles` 次并按 `pollIntervalMs` 睡眠”已经被替换成“由调度层决定何时触发下一轮，每轮重新创建浏览器”的模式。这样更贴近后台巡检任务的真实使用方式，也更容易向 README 解释。

## 登录与验证码链路

### `src/login.ts`

登录模块整体职责没有改变，但它现在适配了新的调度语义。每一轮执行都会重新进入登录检查，因此即使上一轮会话已经失效，也不会要求上层额外关心。

它的职责仍然是：

1. 判断当前页是否已经是讲座页。
2. 必要时打开 SEP 登录页。
3. 填充用户名和密码。
4. 如果存在验证码，则调用验证码模块。
5. 提交登录表单。
6. 如果出现新设备邮箱验证页，则在 `headful` 模式下等待用户人工完成。
7. 登录成功后通过门户中的“人文讲座报名”入口建立 `xkcts` 会话。

### `src/captcha.ts`

验证码模块的识别主线没有被这轮发布整理改变，但它现在被放进了更适合公开仓库说明的上下文里。

它当前的实现事实包括：

1. 会同时生成多种 OCR 候选：
   - `tesseract.js` 原图整词识别
   - `tesseract.js` 阈值图整词识别
   - `tesseract.js` 分割后的单字符识别
   - 可选的 `ddddocr` 原图识别
2. 候选结果会根据长度、来源权重、置信度和字符一致性综合排序。
3. 如果本地没有 `.venv-ddddocr`，系统会自动退回到纯 `tesseract.js` 路径。
4. 验证码失败时最多重试 5 次，避免过高重试频率触发风控。

这意味着公开仓库中的验证码能力现在属于“本地 OCR 增强链路”，而不是某个云端服务的封装。

## 抓取、筛选与报名

### `src/lecture-page.ts`

这个模块继续负责把真实讲座页转换成结构化数据。它仍然保持了“尽量少依赖具体 DOM 细节”的策略，用较宽松的文本归一化方式提取：

1. 标题
2. 开始时间
3. 地点
4. 当前状态
5. 报名入口可用性

### `src/time-window.ts` 与 `src/filter.ts`

这两个模块是本轮重构的重点之一。

此前的筛选规则是硬编码的：

1. 周一 17:00 后
2. 周二 19:00 后
3. 周三全天

现在这套逻辑虽然默认值不变，但已经不再依赖源码常量，而是改成读取配置文件中的时间窗口规则。内部流程变成：

1. `src/config.ts` 把配置文件中的 `filter.timeWindows` 解析成内部时间窗口数组。
2. `src/filter.ts` 在判断讲座是否应该进入候选集合时，把这组时间窗口显式传给时间规则模块。
3. `src/time-window.ts` 根据讲座时间和配置窗口判断是否允许，并生成对应的解释文案。

也就是说，筛选规则已经从“代码逻辑的一部分”转成了“配置驱动的业务规则”。

### `src/register.ts`

报名模块没有引入新的站点逻辑。它仍然负责：

1. 找到报名入口。
2. 点击报名。
3. 捕获确认弹窗。
4. 根据页面或弹窗文本分类结果。

之所以这轮没有重写这里，是因为当前 GitHub 发布整理的重点不在站点行为升级，而在公开可配置性和可说明性。

## 状态持久化

### `src/state-store.ts`

本地状态文件仍然是跨运行去重的基础。现在在定时巡检模式下，这个角色更重要了，因为同一天内会多次触发抓取。

它保存的仍然是两类终态：

1. 已预约
2. 人数已满

以及最近一次读取到的预约次数信息。

对于定时模式来说，这个状态文件的意义是：

1. 避免每小时都重复点击已经满员或已预约的讲座。
2. 让后台巡检不必依赖内存态才能记住历史结果。

## 测试结构

当前测试覆盖已经扩展成五类：

1. 配置文件加载
2. 定时调度计算
3. 时间筛选规则
4. 次数提取
5. 状态文件读写

这意味着本轮新引入的两块核心能力“配置文件模型”和“按时巡检调度”都已经有本地自动化测试约束，而不是只靠 README 描述。

## 当前实现边界

当前实现已经适合公开发布到 GitHub，但仍然保留以下边界：

1. 定时巡检是进程内调度，不是系统级服务；如果系统重启或进程退出，需要由用户自己重新启动。
2. 校外网络下如果再次触发新设备邮箱验证，纯后台 `headless` 模式仍然无法自动完成验证。
3. 过滤规则虽然已经配置化，但当前仍只支持时间窗口，不支持关键词、地点等其他维度。
4. `ddddocr` 仍然是可选增强，不是默认内置依赖。
