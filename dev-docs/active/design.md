# 当前实现设计

## 总体运行流

当前项目的整体结构已经收敛成“配置文件驱动的自动化工具”，而不是一组靠环境变量和长命令拼起来的临时脚本。一次完整运行按以下顺序展开：

1. `src/cli.ts` 启动，调用 `src/config.ts` 读取配置。
2. 配置层把 `.env` 中的敏感信息与 `ucas-bot.config.toml` 中的公开运行参数合并成内部 `AppConfig`。
3. `src/workflow.ts` 根据 `runtime.mode` 决定是执行一轮，还是在配置的时间段里持续巡检。
4. 每一轮执行都会重新创建浏览器上下文，进入登录、建会话、抓讲座、筛选、报名、写状态的主链路。
5. 登录阶段如果遇到验证码，`src/login.ts` 会调用 `src/captcha.ts`，而验证码识别现在统一通过 Python `ddddocr` 脚本完成。
6. 抓取完成后，`src/filter.ts` 和 `src/time-window.ts` 会根据配置文件里的时间段规则决定哪些讲座是候选。
7. 对候选讲座，`src/register.ts` 负责执行真实报名；`src/state-store.ts` 则负责把“已预约 / 满员”等终态写回本地状态文件。

可以把当前实现理解为六层：

1. 配置层：统一读取 `.env` 和 `ucas-bot.config.toml`
2. 调度层：决定单次执行还是定时巡检
3. 登录层：处理 SEP 登录、验证码和人工验证等待
4. 页面抓取层：把讲座页变成结构化讲座数据
5. 规则层：按个人配置的时间段做筛选和停止判断
6. 状态层：持久化终态与次数信息，避免重复访问

## 配置模型

### `.env` 与 `ucas-bot.config.toml`

当前配置模型明确划分职责：

1. `.env`
   只保留 `UCAS_USERNAME` 和 `UCAS_PASSWORD` 这类敏感信息。
2. `ucas-bot.config.toml`
   作为主配置文件，承载公开运行参数。

这意味着 `.env` 和 `ucas-bot.config.toml` 并不重复。程序的运行行为不再通过环境变量描述，而是通过 TOML 配置文件描述；环境变量只承担凭据注入职责。

### `src/config.ts`

这个模块负责三件事：

1. 读取 `.env`
2. 读取 TOML 配置文件，并兼容旧的 JSON 本地文件
3. 使用 `zod` 做结构校验，并转成内部统一结构

当前配置层最重要的内部归一化有三类：

1. `runtime.schedule.periods`
   由用户配置的 `["HH:MM", "HH:MM"]` 数组转换成分钟区间。
2. `filter.timeWindows[*].periods`
   由按星期分组的字符串时间段转换成内部分钟区间数组。
3. `captcha.pythonExecutable`
   统一解析为绝对路径，供验证码模块直接调用。

命令行参数现在只剩少量临时覆盖用途，例如：

1. `--config`
2. `--dry-run`
3. `--no-dry-run`
4. `--headful`
5. `--log-level`

## 调度层

### `src/schedule.ts`

调度辅助模块的职责是“算时间”，而不是执行业务。它当前稳定负责：

1. 判断当前时刻是否落在某个可运行时间段内。
2. 在当前时间基础上，计算下一次巡检应该触发的绝对时刻。

当前调度模型已经不再是“开始小时 + 结束小时”这种单一窗口，而是：

1. 一个时间段数组
2. 一个间隔分钟数

这样同一天里就可以配置多个不连续时间段。

### `src/workflow.ts`

工作流模块分成两层：

1. 顶层调度入口
   根据 `single` 或 `scheduled` 选择执行路径。
2. 单轮执行逻辑
   每轮都独立创建浏览器、登录、抓取、筛选、报名并保存状态。

`scheduled` 模式下当前有几个关键事实：

1. 如果程序启动时已经处于某个可运行时间段内，并且 `runImmediatelyOnStart=true`，会立即跑一轮。
2. 每轮结束后不会简单睡固定毫秒，而是重新计算下一次计划执行时刻。
3. 如果一轮失败，进程不会整体退出，而是记录错误并继续等待下一次执行。

## 登录与验证码

### `src/login.ts`

登录模块的核心职责没有变：

1. 进入 SEP 登录页
2. 填写账号密码
3. 识别是否出现验证码
4. 提交表单
5. 如果出现新设备邮箱验证，在 `headful` 模式下等待人工完成
6. 登录成功后通过门户入口建立 `xkcts` 会话

当前人工验证检测已经收紧到更可靠的口径：优先识别 `https://sep.ucas.ac.cn/user/userVisit` 这类已知验证页，并显式跳过普通 `appStore` 门户页，避免把正常的 SEP 门户误判成邮箱验证页面。

### `src/captcha.ts`

验证码实现已经完全切换为 `ddddocr`，不再保留 `tesseract.js` 路径。当前实现要点如下：

1. 先定位可见的验证码输入框和验证码图片，显式跳过隐藏字段。
2. 对验证码图片截图，并把原图保存到 `.cache/captcha/`。
3. 通过 `execFile` 调用 `scripts/solve-captcha.py`。
4. Python 脚本内部使用 `ddddocr` 识别验证码，并返回 JSON。
5. Node 侧只做结果清洗、长度校验和日志记录，不再承担 OCR 算法本身。
6. 验证码重试次数由配置文件控制，并且上限固定为 5 次。

因此，当前验证码链路的真正运行依赖是：

1. 本地 Python
2. 本地 `ddddocr`
3. 仓库中的 `scripts/solve-captcha.py`

## 抓取、筛选与报名

### `src/lecture-page.ts`

这个模块继续负责把讲座列表页转换成结构化快照，包括：

1. 讲座列表
2. 页面文本
3. 报名次数统计

### `src/filter.ts` 与 `src/time-window.ts`

筛选模块现在的主要变化不是业务规则改变，而是规则表达方式改变。

当前规则模型变成：

1. 每个星期单独配置
2. 每天允许多个不连续时间段

例如“周二上午一段、晚上再一段”这样的规则，现在无需改源码，只需要改配置文件。

### `src/register.ts`

报名模块继续负责：

1. 找到报名入口
2. 执行点击
3. 读取返回文本
4. 把结果分类成成功、已预约、满员或未知

## 状态持久化

### `src/state-store.ts`

状态文件默认保存到 `.cache/lecture-state.json`。当前会记录：

1. 已预约讲座
2. 已满员讲座
3. 最近一次次数统计

这让 `scheduled` 模式可以跨轮次、跨进程跳过已经确定为终态的讲座。

## 运行脚本

为了让公开仓库更容易使用，当前仓库新增了四个操作脚本：

1. `scripts/run-bot.sh`
2. `scripts/run-bot-background.sh`
3. `scripts/run-bot.ps1`
4. `scripts/run-bot-background.ps1`

这些脚本的作用不是替代程序逻辑，而是统一封装跨平台启动方式、Playwright 缓存目录和后台运行入口。

## 当前实现边界

当前实现已经适合公开发布，但边界仍然明确：

1. 邮箱验证依然必须人工完成，后台 `headless` 模式无法自动绕过。
2. 当前筛选规则仍然只支持时间窗口，不支持关键词、地点等其他维度。
3. `ddddocr` 依赖本地 Python 环境，因此项目不是纯 Node 零额外依赖。
4. 定时巡检仍然是进程内调度，而不是系统级守护服务。
