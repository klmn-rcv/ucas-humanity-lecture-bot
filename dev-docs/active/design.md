# 当前实现设计基线

## 总体状态

当前仓库仍处于空白初始化状态，根目录下没有业务代码、配置文件、依赖清单或可执行入口。因此，这个仓库目前不存在实际运行时流程，也没有上游输入、内部处理链路、下游输出或模块间协作关系。

这次 `/spec init` 的作用不是引入业务实现，而是为后续变更建立统一的规范化工作区。初始化完成后，仓库中最核心的结构将是 `dev-docs/`，它用于承载未来的需求说明、执行计划、实现结果和稳定实现知识。

## 当前运行流说明

从运行视角看，仓库当前没有任何可启动程序，也没有构建、测试、服务启动或脚本调度流程。用户进入这个目录时，唯一已经建立的可用结构是规范文档目录本身，因此当前状态可以概括为：

1. 仓库处于未实现业务功能的基线阶段。
2. 没有代码文件可供解释器、编译器或运行时加载。
3. 没有配置驱动的任务流，也没有需要追踪的数据流。
4. 后续所有真实功能都会在这个基线之上，通过 `/spec plan` 和 `/spec go` 逐步引入。

## 目录职责

### `dev-docs/project-meta.yml`

这个文件用于声明仓库已经完成 spec 工作流初始化。后续所有 `/spec` 子命令都应以这里的初始化状态为准，而不是根据目录是否存在来猜测。

### `dev-docs/active/`

这个目录保留“当前活动变更”的工作区，但在初始化阶段它还不代表已经存在某个具体变更。现在只放入 `design.md`，目的是先记录仓库当前实现现状，给未来规划提供基线参照。

### `dev-docs/active/review/`

这个目录预留给后续评审输出。初始化阶段不写入评审内容，只建立位置，确保后续评审文档有固定落点。

### `dev-docs/history/`

这个目录用于归档后续关键变更快照。当前仓库还没有业务实现和变更历史，因此它暂时为空。

### `dev-docs/features/`

这个目录用于记录稳定的实现事实。由于仓库当前没有任何业务代码，这里的内容只需要忠实说明“当前还没有功能实现”这一事实，而不是臆造未来设计。

## 当前设计约束

当前最重要的约束有三点：

1. 不能把初始化文档误当成业务实现。
2. 不能在没有真实代码之前虚构模块关系、数据模型或接口契约。
3. 后续所有功能文档都必须以真实落地代码为依据，逐步扩充，而不是在初始化阶段预先写满未来计划。

## 对后续工作的意义

这份基线文档的价值在于，它明确说明仓库的当前实现边界几乎为零。后续一旦引入代码、配置或脚本，就可以直接在这份说明基础上补充真实运行流、模块职责和依赖关系，而不会把“空仓库”与“已存在但未描述的系统”混为一谈。
