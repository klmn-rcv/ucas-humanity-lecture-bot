# 自动化运行事实

## 主入口与运行方式

当前自动化工具的主入口是 `src/cli.ts`。用户通过 `npm start -- ...` 启动后，CLI 会完成配置读取、日志初始化和主工作流调用。当前已经支持的主要启动模式有：

1. `--dry-run`：只抓取和筛选，不执行真实报名。
2. `--no-dry-run`：执行真实报名流程。
3. `--headful`：显示浏览器窗口，便于观察登录、验证码和页面交互。

## 工作流顺序

`src/workflow.ts` 组织了以下固定顺序：

1. 创建 Chromium 浏览器上下文。
2. 加载本地状态文件。
3. 访问人文讲座页并触发登录检查。
4. 抓取讲座列表与预约次数信息。
5. 应用时间规则和终态跳过规则。
6. 在非 `dry-run` 模式下执行报名。
7. 每轮结束后把最新状态保存到本地。

这个顺序已经是当前实现的稳定事实，因为多个模块之间的输入输出都依赖这条链路。

## 过滤规则事实

当前筛选规则不是通用规则引擎，而是固定业务规则：

1. 周一只允许开始时间在 17:00 及以后。
2. 周二只允许开始时间在 19:00 及以后。
3. 周三任意时间允许。
4. 周四至周日全部排除。

规则实现位于 `src/time-window.ts` 和 `src/filter.ts`，是当前系统最核心的业务约束之一。

## 停止条件事实

系统有两个显式停止条件：

1. 页面显示的“已预约次数”达到或超过“次数要求”。
2. 当前运行已经达到配置的最大轮询次数。

达到第一个条件时，会立即停止新的报名动作；达到第二个条件时，则结束当前程序运行。

## 报名结果判定事实

当前报名结果的稳定判定口径如下：

1. 页面文本出现“成功”“已预约”或“已报名”，视为报名成功或已经处于预约态。
2. 页面文本出现“人数已满”“预约已满”“名额已满”或“满额”，视为人数已满。
3. 其他情况统一归为未知结果，交给日志和后续人工排查。

这套判定目前是文本驱动的启发式实现，而不是来自某个已经验证过的结构化接口。
