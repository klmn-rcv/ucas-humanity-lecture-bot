# 自动化运行事实

## 主入口与启动方式

当前自动化工具的主入口仍然是 `src/cli.ts`，但启动模型已经变成“双层配置 + 少量命令行覆盖”。

稳定事实如下：

1. `.env` 负责敏感信息，例如 UCAS 用户名与密码。
2. `ucas-bot.config.json` 负责非敏感运行配置，例如运行模式、定时巡检窗口、筛选规则、验证码参数和日志级别。
3. 命令行参数只保留少量临时覆盖能力，例如 `--config`、`--dry-run`、`--no-dry-run`、`--headful` 和 `--log-level`。
4. 启动日志会显式输出配置文件路径、是否找到配置文件、运行模式、状态文件路径和筛选规则数量。

## 运行模式事实

当前系统有两个正式运行模式：

1. `single`
   - 执行一次完整的登录、抓取、筛选和报名流程后退出。
2. `scheduled`
   - 在配置的时间窗口内反复执行单轮流程。
   - 当前默认模板配置为每天 `08:00-18:00` 每 `60` 分钟执行一次。

这意味着旧版依赖 `pollIntervalMs` 与 `maxCycles` 的“脚本内循环”已经不再是公开主模型。

## 定时调度事实

定时调度由 `src/schedule.ts` 和 `src/workflow.ts` 协作完成，当前稳定事实如下：

1. 调度模块会判断当前时刻是否落在活动窗口内。
2. 如果启用了 `runImmediatelyOnStart`，并且程序启动时已经位于活动窗口内，则可以立即先执行一轮。
3. 每次巡检完成后，工作流会计算下一次计划执行时间，而不是简单地“睡固定毫秒数”。
4. 如果当天的所有时间槽都已经过去，则下一次计划时间会落到下一天的开始时刻。
5. 定时模式下，每一轮都会重新创建新的浏览器实例和上下文，而不是让同一个浏览器跨全天常驻。
6. 单轮执行失败时，定时模式会记录错误并继续等待下一次计划时刻。

## 当前停止条件事实

在当前实现中，真正会停止单轮业务动作的条件有：

1. 页面显示的已预约次数已经达到或超过总次数要求。
2. 当前轮处于 `dry-run`，因此只输出候选而不继续报名。
3. 进程被用户手动终止，或后台托管工具停止了该进程。

对于定时模式来说，进程本身不会因为完成某一轮而退出；它会持续等待下一次巡检时间。

## 过滤规则事实

当前筛选规则已经不再硬编码在公开使用模型中，而是通过配置文件驱动。

当前仍然只有一类正式支持的筛选：

1. 时间窗口过滤

配置文件中的每一条时间窗口规则都可以指定：

1. `weekday`
2. 可选的 `start`
3. 可选的 `end`

内部判断时，系统会把它们转成“星期编号 + 分钟区间”的内部结构，再交给 `src/filter.ts` 与 `src/time-window.ts` 使用。

## 报名结果判定事实

当前报名结果仍然是文本驱动的启发式判定，稳定口径如下：

1. 页面文本出现“成功”“已预约”或“已报名”，视为报名成功或已处于预约态。
2. 页面文本出现“人数已满”“预约已满”“名额已满”或“满额”，视为人数已满。
3. 其他情况统一归为未知结果，交给日志和后续人工排查。

## 对公开发布的影响

当前运行模型已经适合对外说明，因为它满足以下条件：

1. 用户可以不改源码，仅通过模板文件完成配置。
2. 单次模式和定时模式都能直接由配置文件表达。
3. README 可以把“校园网内单次运行”和“校外后台巡检”清晰分开说明。
