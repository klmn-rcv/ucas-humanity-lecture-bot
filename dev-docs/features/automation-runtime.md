# 自动化运行事实

## 主入口与启动方式

当前自动化工具的主入口仍然是 `src/cli.ts`，但面向公开仓库的推荐启动方式已经变成脚本封装：

1. `scripts/run-bot.sh`
2. `scripts/run-bot-background.sh`
3. `scripts/run-bot.ps1`
4. `scripts/run-bot-background.ps1`

这些脚本最终都会调用 `npm start`，但会顺手统一 Playwright 缓存目录、npm 缓存目录和后台重定向方式。

## 运行模式事实

当前系统有两个正式运行模式：

1. `single`
   执行一次完整的登录、抓取、筛选和报名流程后退出。
2. `scheduled`
   在配置的时间段内反复执行单轮流程。

当前默认模板中的 `scheduled` 示例是：每天 `08:00-18:00` 每 `60` 分钟执行一次。

## 定时调度事实

定时调度由 `src/schedule.ts` 和 `src/workflow.ts` 协作完成。当前稳定事实如下：

1. 调度窗口由 `runtime.schedule.periods` 定义，而不是单一的开始小时和结束小时。
2. 每个时间段使用 `["开始时间", "结束时间"]` 表达。
3. 如果启用了 `runImmediatelyOnStart`，并且程序启动时已经位于某个活动时间段内，会立即先执行一轮。
4. 每轮结束后，系统会计算下一次巡检的绝对时刻。
5. 如果当天所有时间段都已结束，则下一次执行会推到下一天的第一个时间段开始时刻。
6. 定时模式下，每一轮都会重新创建浏览器实例和上下文。
7. 单轮执行失败时，进程不会退出，而是记录错误并等待下一次巡检。

## 停止条件事实

当前会停止单轮报名动作的条件有：

1. 页面显示的已预约次数已经达到或超过总次数要求。
2. 当前轮处于 `dryRun`，因此只输出候选而不执行真实报名。
3. 进程被用户手动停止或被外部托管工具停止。

对于 `scheduled` 模式来说，进程本身不会因为某一轮结束而自动退出。

## 过滤规则事实

当前筛选规则完全由配置文件驱动，且当前只有一类正式支持的筛选：

1. 时间窗口过滤

稳定数据模型如下：

1. `weekday`
2. `periods`

其中每一天允许多个不连续时间段。

## 报名结果判定事实

当前报名结果仍然是文本驱动的启发式判定。稳定口径如下：

1. 页面文本出现“成功”“已预约”或“已报名”，视为报名成功或已处于预约态。
2. 页面文本出现“人数已满”“预约已满”“名额已满”或“满额”，视为人数已满。
3. 其他情况统一归为未知结果，交给日志与后续人工排查。
