# 验证码与状态持久化事实

## 验证码处理事实

当前项目已经实现了验证码存在时的自动处理路径，相关逻辑位于 `src/captcha.ts` 和 `src/login.ts`。

已实现的稳定行为包括：

1. 检测验证码输入框和验证码图片是否出现。
2. 对验证码图片截图，并把原图与阈值化后的处理图保存到 `.cache/captcha/` 供后续排障复盘。
3. 调用 `tesseract.js` 在本地执行 OCR 识别。
4. 对验证码做两类 `tesseract.js` 识别：整词识别，以及把验证码切成四段后的分割识别。
5. 在存在仓库内 `.venv-ddddocr` 环境和 `scripts/ddddocr-experiment.py` 脚本时，额外在验证码原图上调用 Python `ddddocr` 生成 `ddddocr-raw` 候选。
6. 将多个候选结果按字符长度、来源权重、置信度和候选间一致性统一打分，再选择最终要回填的验证码文本。
7. 将识别结果中的非字母数字字符去除后再回填表单。
8. 登录失败且验证码仍存在时，触发验证码刷新并执行有限次重试。
9. 为避免隐藏字段 `#certCode` 干扰可见输入框识别，当前选择器会显式跳过 `type="hidden"` 的输入框。
10. 为避免当前网络环境下 Node `fetch` 的证书链错误，OCR 语言包会先下载到本地 `.cache/tessdata/`，再让 `tesseract.js` 从本地缓存读取。
11. OCR 缓存目录已经固定到 `.cache/tessdata/`，避免语言文件落到仓库根目录。
12. 验证码重试上限已经被配置校验限制为最多 5 次。

## `ddddocr` 集成事实

本轮新增的 `ddddocr` 集成是一个增强候选源，而不是完全替换 `tesseract.js`。当前稳定事实如下：

1. `ddddocr` 的运行依赖是仓库内的 `.venv-ddddocr/bin/python`。
2. Node 主流程不会直接嵌入 Python 解释器，而是通过 `execFile` 调用 `scripts/ddddocr-experiment.py`，并读取其 JSON 输出。
3. 如果 `.venv-ddddocr/bin/python` 或 `scripts/ddddocr-experiment.py` 不存在，主流程会静默跳过 `ddddocr` 候选，继续使用原有 `tesseract.js` 路径，不会导致登录流程失败。
4. `ddddocr` 当前只识别验证码原图，不参与阈值图或分割图的识别。
5. `ddddocr` 输出通常偏向小写，因此主流程会结合其他候选的相同字符位置，对其字母大小写做一次对齐修正后再参与最终打分。

## 2026-03-17 现场验证补充

基于 2026-03-17 的真实现场验证，当前可以确认以下新增事实：

1. SEP 登录页在特定网络环境下会真实出现验证码。
2. 当前实现已经真实打出了 `captcha.detected` 和 `captcha.solved` 日志，说明验证码检测、截图和 OCR 已经现场跑通。
3. 在引入 `ddddocr` 之前，验证码路径能够登录成功，但有时需要第 2 次尝试。
4. 在引入 `ddddocr` 之后，最新一次真实 `--headful --dry-run --log-level debug` 以 `variant=ddddocr-raw` 在第 1 次尝试就通过验证码并进入讲座页。
5. 已缓存的多张真实验证码样本表明，`ddddocr` 在原图上的结果明显优于当前仅使用 `tesseract.js` 时的主要失败样本。
6. 当前实现不会自动处理 SEP 的邮箱/手机二次安全验证，但在 `headful` 模式下会识别该页面并等待用户人工完成。

## 验证码边界事实

虽然当前 OCR 路径已经经过真实样本增强，但以下边界仍然成立：

1. `ddddocr` 依赖 Python 虚拟环境，不属于纯 Node 自包含依赖。
2. 当前并没有为 `ddddocr` 建立单独的 Node 侧单元测试，验证主要来自真实样本批量实验和真实网页登录。
3. 当前样本量仍然有限，尚不能把验证码模块视为“完全收敛”的稳定高精度组件。

## 状态文件事实

本地状态持久化由 `src/state-store.ts` 管理，默认保存到 `.cache/lecture-state.json`。当前状态文件保存的稳定内容包括：

1. 已预约讲座的标识、标题和时间戳。
2. 人数已满讲座的标识、标题和时间戳。
3. 最近一次读取到的预约次数信息。

## 状态文件使用方式

状态文件在当前实现中承担两个明确职责：

1. 跨运行跳过已经确认终态的讲座，避免重复点击和重复报名。
2. 为后续排障提供最小可追溯信息，例如某个讲座是何时第一次被判定为已预约或人数已满。

当前状态文件不承担历史归档、统计报表或多用户同步功能。
