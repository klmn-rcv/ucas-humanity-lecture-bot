# 验证码与状态持久化事实

## 验证码处理事实

当前项目已经实现验证码存在时的自动处理路径，相关逻辑位于 `src/captcha.ts` 和 `src/login.ts`。

当前稳定行为包括：

1. 检测验证码输入框和验证码图片是否出现。
2. 对验证码图片截图，并把原图保存到 `.cache/captcha/` 供后续排障复盘。
3. 调用本地 Python 可执行文件运行 `scripts/solve-captcha.py`。
4. Python 脚本内部使用 `ddddocr` 返回验证码识别结果。
5. Node 侧对识别结果做清洗、长度校验和日志记录后再回填表单。
6. 登录失败且验证码仍存在时，会刷新验证码并在上限范围内重试。
7. 为避免隐藏字段 `#certCode` 干扰可见输入框识别，当前选择器会显式跳过 `type="hidden"` 的输入框。
8. 验证码重试上限已经被配置校验限制为最多 5 次。

## `ddddocr` 集成事实

当前验证码实现已经统一为 `ddddocr`，稳定事实如下：

1. `ddddocr` 的运行依赖是本地 Python 环境。
2. Python 可执行文件路径通过 `captcha.pythonExecutable` 配置。
3. Node 主流程不会嵌入 OCR 算法，而是通过 `execFile` 调用 `scripts/solve-captcha.py` 并读取其 JSON 输出。
4. 当前不再保留 `tesseract.js` 作为备用路径。
5. 如果 Python 可执行文件或脚本路径不存在，登录流程会明确报错，而不是悄悄退回另一套 OCR。

## 验证码边界事实

以下边界仍然成立：

1. 当前并没有在 Node 侧为 `ddddocr` 建立独立单元测试，验证主要来自配置测试和真实站点现场验证历史。
2. 当前 OCR 成功率仍然依赖真实验证码样式和本地 Python 环境。
3. 当前系统不会自动处理 SEP 的邮箱/手机二次安全验证，只会在 `headful` 模式下等待用户人工完成。

## 状态文件事实

本地状态持久化由 `src/state-store.ts` 管理，默认保存到 `.cache/lecture-state.json`。当前状态文件保存的稳定内容包括：

1. 已预约讲座的标识、标题和时间戳。
2. 人数已满讲座的标识、标题和时间戳。
3. 最近一次读取到的预约次数信息。

## 状态文件使用方式

状态文件在当前实现中承担两个明确职责：

1. 跨运行跳过已经确认终态的讲座，避免重复点击和重复报名。
2. 为后续排障提供最小可追溯信息，例如某个讲座是何时第一次被判定为已预约或人数已满。
