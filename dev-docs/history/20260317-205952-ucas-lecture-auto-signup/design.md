# 当前实现设计

## 总体运行流

当前仓库已经实现了一个基于 Node.js 的命令行自动化工具，主入口是 `src/cli.ts`。一次完整运行的流程如下：

1. CLI 启动后先读取环境变量和命令行参数，建立运行配置，包括账号密码、讲座页地址、状态文件位置、轮询次数、`dry-run` 模式和验证码 OCR 参数。
2. 主工作流创建 Playwright Chromium 浏览器上下文，然后尝试直接访问人文讲座页面。
3. 如果访问过程中被重定向到 SEP 登录页，登录模块会填充用户名和密码；若页面出现验证码输入框，则先截图验证码图片，调用本地 OCR 识别文本并回填，再提交登录表单。
4. SEP 登录成功后，并不会直接具备 `xkcts` 讲座页会话。当前真实可用路径是先进入 SEP 门户页，再通过其中的“人文讲座报名”入口建立单点登录会话，然后再访问 `https://xkcts.ucas.ac.cn:8443/subject/humanityLecture`。
5. 讲座抓取模块会读取讲座列表页的表格行和页面全文，提取讲座标题、开始时间、地点、状态和报名按钮文案；如果讲座页本身没有次数信息，则再尝试访问“报名及听课记录”页补充统计信息。
6. 过滤模块根据固定时间窗口判断每个讲座是否符合报名条件，同时结合本地状态文件中已记录的“已预约 / 人数已满”讲座做去重与跳过。
7. 如果页面显示已预约次数已经达到要求，工作流直接停止，不再执行新的报名动作。
8. 在 `dry-run` 模式下，工具只输出候选讲座；在真实执行模式下，工具会顺序点击讲座行中的报名入口，并根据页面反馈把讲座记为报名成功、已预约或人数已满。
9. 每个周期结束后，最新的终态讲座信息和次数信息会被写回本地状态文件，供下一次运行复用。

整个系统的关键关系是：CLI 负责组织输入，浏览器会话层负责拿到受保护页面，讲座抓取层负责把页面转换成结构化数据，过滤和状态层负责控制“应该报名什么”，报名层负责执行点击和结果回写。

## 代码结构说明

### `src/cli.ts`

这是命令行入口。它只负责三件事：加载配置、创建日志器、调用主工作流。这样做的目的是把启动逻辑和业务逻辑分离，避免入口文件同时承担页面自动化和业务判断。

### `src/config.ts`

这个模块统一处理环境变量和命令行参数。它使用 `zod` 做配置校验，确保缺少用户名、密码或参数格式错误时，程序会尽早失败，而不是在浏览器已经启动后才出现难以定位的错误。

这里还把 `headful`、`dry-run`、状态文件路径、轮询次数、验证码重试次数等运行参数都收敛成一个 `AppConfig` 对象，后续模块不需要再直接读取 `process.env`。

### `src/log.ts`

日志模块输出结构化 JSON 行。每条日志都带时间、级别和事件名，目的是让后续排障时能快速区分是登录问题、验证码问题、时间过滤问题，还是报名动作本身出了问题。

### `src/login.ts` 与 `src/captcha.ts`

这两个模块共同负责登录链路。

`src/login.ts` 的职责是：

1. 判断当前页面是否已经是讲座页。
2. 必要时跳转到 SEP 登录页。
3. 填写用户名和密码。
4. 如果验证码输入框可见，则调用 OCR 模块处理验证码。
5. 提交表单，检查是否仍然停留在登录页，并在失败时执行有限次重试。
6. 如果 SEP 会话已经建立，则不重复填表，而是直接复用现有 SEP 会话。
7. 通过 SEP 门户中的“人文讲座报名”入口进入 `xkcts`，建立真正可访问讲座页的会话。

`src/captcha.ts` 的职责更窄，只处理验证码本身：检测验证码是否可见、截图验证码图片、调用 `tesseract.js` 识别文本，以及在失败场景下刷新验证码。这样后续如果要替换 OCR 引擎，只需要修改这里而不是改整个登录流程。

### `src/lecture-page.ts`

这个模块负责把讲座列表页面转换成内部结构。它不会假设页面一定是某个固定表格库，而是用比较宽松的选择器抓取常见的表格行和操作按钮，再根据文本内容推断：

1. 哪一行像是有效讲座记录。
2. 该行的标题可能是什么。
3. 开始时间文本是什么。
4. 当前状态更接近“可报名”“已预约”还是“人数已满”。
5. 哪个按钮或链接可能对应报名动作。

这套实现的核心目的是面对真实页面结构未知的情况时，先用尽可能稳妥的文本归一化方式把信息抓出来，而不是过早把逻辑写死在某个未验证过的 DOM 结构上。经过真实站点验证后，当前实现已经确认能识别出“已经预约过”和“预约已结束”这类真实状态文案。

### `src/time-window.ts` 与 `src/quota.ts`

这两个模块承载固定业务规则。

`src/time-window.ts` 负责解析讲座开始时间，并实现固定时间窗口判断：周一 17:00 及以后、周二 19:00 及以后、周三任意时间。它还会返回解释文本，用于日志和排障。

`src/quota.ts` 负责从页面全文中提取“已预约次数 / 次数要求”。在真实站点上，这类信息不在讲座预告页，而在“报名及听课记录”页中以“累计听讲座 / 其中有效 / 有效记录 15 次及以上”的形式出现。这个模块不参与页面点击，只负责把页面文案变成明确的数字判断，供主工作流决定是否停止。

### `src/state-store.ts`

本地状态文件的职责是跨运行保存终态讲座。当前仅保存两类终态：

1. 已预约
2. 人数已满

这样工具在下一次运行时，即使再次抓到同一条讲座，也会优先跳过，避免重复访问和重复点击。状态文件同时保存最近一次读到的次数信息，方便后续判断系统是否已经接近目标。

### `src/filter.ts`

过滤模块把页面抓取结果和本地状态结合起来，给每个讲座输出一个明确决策：

1. 跳过
2. 候选
3. 停止

它的判断顺序是刻意设计过的：先看是否已经达到总次数要求，再看本地终态记录和页面终态状态，最后才看时间窗口和是否存在可点击入口。这样可以尽量减少对不必要讲座的后续处理。

### `src/register.ts`

报名模块只负责执行“点击”和“读取结果”。它会根据列表行索引找到相应的按钮，尝试点击报名入口，自动接受可能出现的确认弹窗，并从页面文本中推断报名结果是成功、已预约、人数已满还是未知。

由于当前没有真实登录后的 DOM 样本，这里的实现仍然采用通用型策略，而不是绑定某个具体弹窗组件。

### `src/workflow.ts`

这是整个系统的编排层。它负责：

1. 启动浏览器。
2. 载入本地状态。
3. 循环执行登录、抓取、过滤和报名。
4. 在每次报名后刷新页面，重新判断次数是否已达要求。
5. 把最终状态持久化。

因此它承担的是流程控制，而不是具体页面解析或单条规则判断。这样当规则或页面解析需要调整时，可以尽量不动整体编排。

## 测试与验证结构

当前仓库已经建立 `vitest` 测试，覆盖了三类不依赖真实账号的核心规则：

1. 时间窗口解析与筛选。
2. 次数提取与停止条件判断。
3. 状态文件记录逻辑和配置解析。

另外，CLI 也经过了最小 smoke test 验证：在缺少凭据时会输出明确错误，而不是直接出现无上下文崩溃。

## 当前实现边界

虽然核心代码已经完成，但仍然存在一个明确边界：没有真实登录后的页面样本，因此讲座表格字段提取和报名反馈判断采用的是通用型启发式实现。它已经足够支撑后续带凭据的现场验证，但如果真实页面结构和预期差异较大，还需要在下一轮基于真实 DOM 进一步收紧选择器与结果判定逻辑。
